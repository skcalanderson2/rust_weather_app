Migration case study

Porting WeatherApp from Xojo to Rust

A Raspberry Pi weather display, rewritten in Rust with the iced GUI toolkit over a few sessions with an AI coding assistant. The project is small, but the steps apply to moving most desktop or embedded GUI apps off a commercial toolchain.

Source: Xojo 2025r2 project Target: Rust + iced 0.14 Device: Raspberry Pi, 64-bit Bookworm, 800×480 Result: ~680 lines of Rust, 6 tests
User Claude

Every log entry below is tagged with who did it. The user owned the hardware, the network and every decision about scope; Claude did the reading, coding, building and verifying it could reach from the Mac.

01

State the reason and the constraints

A rewrite needs a concrete reason, and that reason sets the scope. Here it was licensing cost, so the goal was the same app on a free toolchain rather than a new app.

  • User

    Explained that Xojo licence fees had become too expensive, asked for a Rust + iced rewrite for a Pi running Raspberry Pi OS, and supplied the project files (XML and binary) plus a screenshot of the running app. Pointed out that data comes both from web APIs and from a local temperature sensor.

A screenshot of the working app is the most useful thing you can hand over. It becomes the acceptance test.

02

Read the old project as data

Most GUI builders store projects in a structured format: XML, JSON, or a text DSL. Parse it to get every constant, event handler, timer and control position. Do this before writing any code.

  • Claude

    Found that the 900 KB XML file was mostly image references. Stripped them, leaving about 115 KB of real content: an App module, one window, three HTTP socket subclasses and 236 icons.

  • Claude

    Pulled out the logic: the Open-Meteo forecast URL (home latitude and longitude, °F, mph, America/Denver), two sensor URLs on the LAN, a 1-second clock timer, a 15-minute refresh timer, Esc to quit, and a hidden cursor.

  • Claude

    Recorded every label's position, size, font size and colour (for example the clock at x 20, y 20, 348×115, Arial 80, #CCCCCC), so the new layout could match the old one exactly.

  • Claude

    Noted dead code and quirks: a WMO weather-code table that was built but never used; an icon choice limited to three images; a second icon canvas that pointed at a missing image; no error handling on the sensor calls; and a number format that would print 70. for whole numbers.

  • Claude

    Called the live forecast API to confirm the real JSON shape. Tried the sensor too; it was unreachable from the Mac at that point.

Calling the real APIs before you design the data types means your types come from the actual JSON, not from guesses or out-of-date docs.

03

Ask only the questions that change the build

After reading the project, the open questions were few and specific. Each one had a sensible default, so the questions could be quick multiple-choice.

  • Claude

    Asked four questions: faithful port or improvements; which Pi and OS; build on the Pi or cross-compile; and config or deployment extras.

  • User

    Chose a faithful port with small fixes, a 64-bit Pi 4/5 on Bookworm, building natively on the Pi, and a TOML config file. Declined autostart and icons embedded in the binary.

"Faithful port plus small fixes" is usually the right scope. Bugs found while reading get fixed. New features wait until the port works.

04

Map each old concept to its Rust equivalent

Event-driven GUI builders and Rust's Elm-style toolkits (iced, Relm4, Slint) differ in shape but cover the same concepts. Write the mapping down. It doubles as the design doc.

XojoRust / iced
Window controls with propertiesOne App struct holding state; a pure view() that builds widgets from it
Timer with Periodtime::every(Duration) subscription producing a Message
URLConnection.ContentReceived eventTask::perform(async fetch, Message::Loaded) with reqwest
ParseJSON into a DictionaryTyped serde structs; bad data fails at parse time
Error eventResult<T, String> in the message, plus a retry task
Constants on Appconfig.toml with defaults equal to the old constants
Labels at absolute x/ypin(...).x().y() inside a fixed 800×480 stack!
Canvas Backdrop imageimage(Handle::from_path(...))
KeyDown Esc → Quitkeyboard::listen() filtered to Escape → iced::exit()
System.Cursors.InvisibleCursormouse_area(...).interaction(Interaction::Hidden)
  • Claude

    Wrote the analysis and this mapping into PLAN.md. Started a helper agent to read the iced 0.14 source for exact API signatures, which had changed since earlier versions (keyboard::listen replaced on_key_press; pin is new). Wrote the data layer in parallel.

GUI toolkit APIs change between minor versions. Check the source of the version you actually depend on before relying on a tutorial.

05

Build the data layer first, with tests

Fetching and parsing the data is where a port most often breaks quietly, and it is the easiest part to test. Lock it down before touching the UI.

  • Claude

    Split the code into three modules: config.rs (TOML, file lookup, defaults), weather.rs (serde models, async fetchers, WMO-code→icon mapping, number formatting) and main.rs (UI).

  • Claude

    Wrote six unit tests. One checks that the generated forecast URL matches the Xojo constant character for character. Others parse the real API response and the sensor JSON, compare number formatting with Xojo's output, and confirm that every icon the mapping can return exists on disk.

  • Claude

    Copied the 128 px icon set (MIT licensed) and the gradient background into assets/ from the user's original Xojo folder.

#[test]
fn default_url_matches_xojo_format() {
    let xojo = "https://api.open-meteo.com/v1/forecast?latitude=39.7392&...";
    assert_eq!(Config::default().forecast_url(), xojo);
}

A test that compares new output with the old program's output is the cheapest way to prove the port behaves the same.

06

Rebuild the UI, then compare it with the original

Put each control where the old one was, then check the result against the reference screenshot. A visual diff catches problems that unit tests can't.

  • Claude

    Built the iced view from the recorded coordinates. Each source (forecast, sensor temperature, sensor humidity) fetches independently, so one failure can't block the others. A failed source retries after 60 seconds instead of waiting 15 minutes.

  • Claude

    Ran it on macOS against a mock sensor. The build, tests and clippy were clean, but macOS blocked the screenshot, so the visual check was handed to the user.

  • User

    Granted screen and network access so Claude could run it again on the Mac.

  • Claude

    Re-ran against the real sensor. The screenshot matched the original layout. It also showed one bug: small bold labels fell back to a monospace font because the configured font wasn't installed on the Mac. Claude made the font configurable with a system-default option and confirmed the fix with a second screenshot.

  • Claude

    Spotted that the sensor reported 1% humidity, which can't be right, and flagged it to the user.

Font fallback is the most common visual difference after a port. Name a font that is actually installed on the target, and check bold weights as well as regular.

07

Get the binary onto the device

Building on a small board can fail even when the code is fine. Plan from the start how the binary gets onto the device.

  • User

    Asked how to mount the Synology NAS on the Pi over NFS, then pasted each error back as it happened.

  • Claude

    Wrote the /etc/fstab entry (_netdev,nofail,x-systemd.automount). From the pasted showmount output, Claude found the cause of "access denied": the share's permission rule allowed 196.168.88.0/24 instead of 192.168.88.0/24, and the Drive folder sits under /volume1/homes/sysala/Drive.

  • User

    Fixed the rule in DSM and confirmed the mount worked. Then tried a native cargo build --release on the Pi; it froze at crate 140 of 441 after running out of memory.

  • Claude

    Gave a swap-and-fewer-jobs workaround. When the user asked about cross-compiling, Claude installed cargo-zigbuild and built for aarch64-unknown-linux-gnu.2.36 on the Mac in 59 seconds. The result was a 19 MB binary that links only against glibc (2.35 at most, below Bookworm's 2.36). Claude also wrote build-pi.sh, which packages the binary with its assets.

  • User

    Unpacked the tarball from the NAS mount onto the Pi and confirmed the app runs as specified.

cargo install --locked cargo-zigbuild
rustup target add aarch64-unknown-linux-gnu
cargo zigbuild --release --target aarch64-unknown-linux-gnu.2.36

Add the target's glibc version to the target triple (.2.36) so the binary runs on the device's OS release. Zig acts as the cross-linker, so you don't need Docker or a Linux sysroot.

08

Fix what the port brought to light

A careful rewrite brings up long-standing problems in the whole system, including the parts outside the app.

  • User

    Explained that the outdoor DHT22 had always reported wrong humidity, and shared its CircuitPython code.

  • Claude

    Found no bug in the reading code: it used the right DHT22 driver and passed the value through unchanged. Because the library checks a checksum on every reading, the sensor itself must be sending 1%, which is a common failure for DHT22s left outdoors. Suggested a breath test to confirm, and a sturdier sensor (SHT31, SHT41 or BME280) in a radiation shield.

  • Claude

    Rewrote the sensor endpoints with retries and an HTTP 503 response on failure. The Rust app already handles a 503 by keeping the last good value.

Checklist for your own migration

  1. Write down why you're porting. It decides how much you change.

  2. Collect the old project, a screenshot of it running, and every external endpoint it calls.

  3. Export or parse the project into text. List the constants, timers, event handlers, control positions and fonts.

  4. Call each API and save a real response to use as a test fixture.

  5. List the dead code and quirks, and decide which to keep for fidelity and which to fix.

  6. Map each old concept to the Rust toolkit. Check the toolkit version you actually use.

  7. Build the config and data layers first. Test them against the old program's output.

  8. Rebuild the UI from the recorded geometry, then compare it with the screenshot on the real display.

  9. Plan the deployment early. Cross-compile if the target is small, and pin the target's glibc version.

  10. Package the binary with its assets and config so deploying is a single copy.

  11. Have the person who owns the device confirm it works there.
